배터리 주문 프로그램 이해 문서

독자: 신입 개발자 · 리뷰 중점: 계산·업무 규칙 정확성 · 코드에서 직접 확인한 내용만 적었고, 확인하지 못한 것은 "확인 필요"로 표시했습니다. 개발 용어는 점선 밑줄에 마우스를 올리면 뜻이 보입니다.

1. 3줄 요약

  1. 외국 배터리 공장 4곳(중국, 일본, 베트남, 인도네시아)에 "얼마나 만들어 달라"고 주문하는 프로그램입니다.
  2. 만든 배터리를 배로 한국에 가져오는 길을 "가장 싼 길 / 가장 빠른 길 / 가까운 곳부터 가는 길" 세 가지로 계산해 줍니다.
  3. 마음에 드는 길을 고르면 주문이 확정되고, 그 뒤로 "진행 → 완료"로 상태를 관리합니다.

2. 누가, 무엇을 하나

사용자는 로그인한 담당자 한 종류뿐입니다. 하는 일은 네 단계입니다.

3. 업무 규칙

규칙 대부분은 계산기 클래스의 설명 주석(Planner.java:15-26)에 적혀 있고, 아래는 그 규칙이 코드 어디에 구현됐는지를 함께 보여 줍니다.

  • 생산: 주문 즉시(0일차) 모든 공장이 동시에 시작합니다. 하루 생산 = min(하루 최대, 재고 상한 − 현재 재고, 남은 주문). Planner.java:402
  • 수거: 배는 도착한 날 그 공장 재고를 전부 싣습니다. 수거량이 그날 재고와 다르면 예외를 던집니다. Planner.java:393-397
  • 방문 횟수: 올림(주문 ÷ 재고 상한). 마지막 방문 전까지는 재고 상한만큼, 마지막은 나머지를 싣습니다. Planner.java:39-47, 84-98
  • 한 나라, 한 배: 나라들을 "배 한 척이 맡을 묶음"으로 나누는 모든 방법을 만들어 시도하므로 자동으로 지켜집니다. Planner.java:101-127
  • 왕복: 여러 번 수거하면 한국에 돌아와 내려놓고 다시 출항합니다. 한 왕복 안에서는 항해 일수가 가장 짧은 방문 순서를 씁니다. Planner.java:213-224
  • 늦게 출항: 출항일 = max(배가 한국에 돌아온 날, 각 방문지의 "준비 완료일 − 거기까지 가는 일수"). 한국 대기는 무료입니다. Planner.java:318-324
  • 비용: 생산비 = 수량(K) × 1,000 × 셀당 원가. 운항비 = 바다에서 보낸 날수 × 배 하루 운항비. Planner.java:362, 341
  • 세 가지 길: 운항비 최소(비용이 같으면 더 빠른 쪽) / 가장 빠르게(일수가 같으면 더 싼 쪽) / 가까운 곳부터(한국에서 가까운 나라를 배에 돌려 배정). Planner.java:56-78, 255-284
  • 한도: 총 주문 1K ~ 100,000K, 배 1~4척. BatteryService.java:197-216, 36

5. 예시 따라가기

처음 값 그대로 네 공장에 3,000K씩(총 12,000K) 주문하고 "운항비 최소" 길을 고른 경우입니다. 숫자는 PlannerTest.defaultOrderSummary를 실제로 돌려 얻은 값입니다.

요청이 들어온다

"시뮬레이션" 버튼 → POST /api/simulate → AppController.simulate(172) → BatteryService.simulate(190). 수량이 음수이거나 합계가 0 이하·100,000 초과면 여기서 거절합니다(197-216).

방문 횟수 계산 · Planner.visits

중국 3,000 ÷ 4,000 → 1번 · 일본 3,000 ÷ 2,000 → 2번(2,000K + 1,000K) · 베트남 1번 · 인도네시아 1번.

코드 보기
result.put(c, q <= 0 ? 0 : (q + limit - 1) / limit);   // Planner.java:44 올림 나눗셈

후보를 모두 만든다 · Planner.plan

나라 4개를 배 한 척이 맡을 묶음으로 나누는 모든 방법(최대 15가지)을 만들고, 각 묶음의 왕복 구성과 방문 순서를 정해 schedule로 일정을 계산합니다. 그중 운항비가 가장 낮은 것이 "운항비 최소", 일수가 가장 짧은 것이 "가장 빠르게"입니다(56-72).

출항일 계산 · Planner.schedule

공장 준비 기간: 일본 2,000K ÷ 800 → 3일, 중국 3,000K ÷ 400 → 8일, 인도네시아 3,000K ÷ 300 → 10일, 베트남 3,000K ÷ 200 → 15일(병목).

코드 보기
int ready = lastPickup.getOrDefault(c, 0) + ceilDiv(amount, master.factory(c).maxDaily());
depart = Math.max(depart, ready - offset[i]);   // Planner.java:322-323

선택된 안: 배 1척이 두 번 왕복

첫 왕복: 일본이 3일이면 준비되고 한국에서 2일 거리 → 1일차 출항, 3일차 도착(2,000K 적재), 5일차 귀환. 바다 4일.
두 번째 왕복: 베트남(15일)에 맞춰 10일차 출항 → 중국 11일 → 베트남 15일 → 인도네시아 17일 → 일본 24일(남은 1,000K) → 26일차 귀환. 바다 16일.

비용과 검산 · toPlan / simulateFactory

생산비 = 중국 21억 + 일본 27억 + 베트남 16.5억 + 인도네시아 13.5억 = 78억. 운항비 = (4 + 16)일 × 1억 = 20억. 합계 98억 원, 26일.

마지막으로 하루씩 시뮬레이션하며 "수거량 = 그날 재고", "주문을 전부 수거했는가"를 검산하고, 어긋나면 예외를 던집니다(386-411).

다른 두 길과 비교

운항비 최소26일20억98억1척

배 3척이면 6일 빨라지는 대신 12억이 더 듭니다. 생산비(78억)는 어느 길이든 같습니다.

확정 · BatteryService.confirm

같은 입력으로 다시 계산 → 기준 값 번호 비교 → 고른 길 선택 → 주문과 상태 이력(확정) 저장(225-248).

6. 리뷰 포인트 — 계산·업무 규칙 정확성

"의심해 볼 만한 곳"이지 "틀렸다"는 뜻이 아닙니다. 확인 필요는 의도인지 실수인지 요구사항 담당자에게 물어야 하는 항목입니다. 각 항목 아래 "확인 방법"은 리뷰하면서 해 볼 수 있는 일입니다.

  • 확인 필요"운항비 최소"는 전체 중 최소인가, 시도한 안 중 최소인가 같은 나라를 여러 왕복에 나눠 들를 때 "앞쪽 / 뒤쪽 / 고르게" 세 가지 배치만 만듭니다. 예를 들어 방문 횟수가 왕복 수보다 적은 나라가 어느 왕복에 들를지, 세 가지 패턴 밖의 조합은 시도하지 않습니다. 그래서 이름이 약속하는 "최소"가 "시도한 안 중 최소"일 수 있습니다. Planner.java:139-210 확인 방법: 방문 횟수가 서로 다른 입력(예: 중국 4,001 / 일본 9,000)으로 배치를 직접 전부 만들어 비교하는 테스트를 작성해 본다.
  • 확인 필요항구 대기·짐 싣는 시간 0일 도착일과 출발일이 같게 만들어집니다(new Stop(c, arrive, arrive, …)). 하역 시간을 무시하는 것이 요구사항인지 확인이 필요합니다. Planner.java:330
  • 극단 입력에서 계산량이 폭발하지 않는가 재고 상한은 1까지, 총 주문은 100,000K까지 허용합니다. 이 경우 방문 횟수가 수만 번이 되어 왕복 목록과 일별 배열이 매우 커지고, 후보마다 반복됩니다. 실제 소요 시간은 측정하지 못했습니다. BatteryService.java:138 · Planner.java:33, 84-98, 173-197 확인 방법: 재고 상한 1, 총 100,000K로 Planner.plan 시간을 재 본다.
  • 자체 검산 실패가 사용자에게 어떻게 보이는가 어긋나면 IllegalStateException을 던지는데, 컨트롤러는 BusinessException만 잡습니다. 그래서 사용자에게는 안내 문구 대신 일반 서버 오류가 나갈 수 있습니다. 실제 화면은 확인하지 못했습니다. Planner.java:395, 409 · AppController.java:174-179
  • 항로가 "직접 이동"만 고려됨 방문 순서는 두 나라 사이 직접 항해 일수만 씁니다. 기준 값 화면에는 "직접 가는 것이 한국을 거치는 것보다 빠르다"는 검사가 없어, 값을 이상하게 넣으면 직접 항로가 더 느린데도 그 길을 쓸 수 있습니다. Planner.java:226-234 · BatteryService.java:144-152
  • "가까운 곳부터"는 의도적으로 단순한 규칙 가까운 나라부터 배에 돌아가며 배정하고, 각 왕복에서도 가까운 나라 순서로 들릅니다. 최적화를 하지 않으므로 보통 "운항비 최소"보다 비싸지만, 이를 확인하는 테스트는 기본 주문 한 가지뿐입니다. Planner.java:255-284 · PlannerTest.java: costOptionIsNotMoreExpensive…
  • 기대값을 고정한 테스트가 부족하다 기본 주문(3,000K × 4)의 결과를 출력만 하는 테스트(defaultOrderSummary)는 있지만 "26일, 98억" 같은 값을 단언하지는 않습니다. 계산 규칙이 바뀌어도 이 값이 조용히 달라질 수 있습니다. 반면 "수거량 = 주문량", "한 나라 한 배", "생산비 = 수량 × 원가" 같은 성질은 테스트로 보호됩니다. PlannerTest.java: defaultOrderSummary 확인 방법: 위 3가지 길의 일수·비용을 그대로 단언하는 테스트를 추가해 본다.
  • 좋음비용 계산 단위가 안전하다 금액은 모두 long으로 계산합니다. 총 주문 한도(100,000K) × 1,000 × 셀당 원가 상한(1억)도 long 범위 안입니다. Planner.java:362 · BatteryService.java:139
  • 좋음계산기가 스스로 검산한다 일정을 만든 뒤 하루씩 생산·재고를 다시 시뮬레이션해서 수거량과 주문 완료 여부를 확인합니다. 일정 계산 오류를 조기에 드러내는 장치입니다. Planner.java:386-411
