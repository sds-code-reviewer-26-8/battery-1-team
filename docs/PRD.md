# PRD — 배터리 주문·생산·선박 운영 계획 프로그램 (취합본)

> 취합 대상: 권웅기(권), 김도현(도), 김재연(재), 김준영(준) — 4명 전원
> 4명이 같은 내용을 적은 것은 그대로 올렸다. 일부만 적었거나 의견이 갈리는 것은 항목 끝에 **(권/도/재/준)** 으로 출처를 적었고, 갈리는 것은 **[미정 Ax]** 로 표시했다. `Ax`, `Bx`, `Dx`는 `docs/취합-차이표.md`의 ID다.
> 이 취합본은 어느 쪽이 맞는지 정하지 않았다.

## 1. 개요

해외 4개국(중국·일본·베트남·인도네시아) 공장에서 만든 배터리 셀을 배로 한국에 가져오는 계획을 계산해 주고, 담당자가 고른 계획을 주문으로 확정·관리하는 웹 애플리케이션이다. 주문 수량을 넣으면 공장별 생산과 선박 운항 계획을 비용·기간과 함께 비교해 볼 수 있다.

해결하려는 문제
- 빠르게 받을지, 싸게 받을지에 따라 답이 달라서 비교할 수 있어야 한다. (도)
- 확정한 주문의 계획과 비용은 나중에도 그대로 남아 있어야 한다. (도)

업무 배경 (요구사항 원문, 재 정리)
- DSD는 한국 본사의 배터리 생산·공급 기업이고, 전기차용 원통형 **2170 셀**을 만든다. 차량 1대에 약 4K개가 들어간다.
- 중국·일본·베트남·인도네시아 4개국에서 공장을 직접 소유·운영하고, 모든 공장이 같은 배터리를 만든다.
- 주문이 접수되면 가능한 빨리 생산을 시작해 각 공장의 완제품 재고 창고에 보관한다. 공장마다 하루 최대 생산량, 재고 보관 용량, 생산원가가 다르다.
- 임차한 화물선 1~4척으로 한국에 들여온다. 선박은 하루 대당 약 1억 원이고, 한국 항만에 정박 중에는 비용이 없다. 컨테이너 적재량은 충분하다.
- 비용은 생산원가(셀당 500~1,000원 수준), 공장 운영비(국가별 상이), 선박 임차비로 나뉜다.

## 2. 사용자

- 주문 담당 관리자 1계정. 로그인한 사람만 시스템을 쓴다.
- 로그인을 요구사항으로 볼지, 코드에만 있는 기능으로 볼지 **[미정 A5]**

## 3. 범위

포함: 마스터 데이터 관리, 경로 시뮬레이션, 주문 확정, 주문 조회, 주문 상태 관리

제외
- 실시간 운항·생산 추적, 외부 시스템 연동 (준/재)
- 다중 계정·권한 구분 (준/재)
- 확정 후 주문 수량·경로 수정 (재)

추가 개발 대상 **[미정 A2]**: 고객사 입력, 필요 납기 입력, 국가별 공장 운영비 (권/재. 요구사항 원문에 "추가 개발 필요"로 적혀 있음)

## 4. 용어

| 용어 | 뜻 |
|---|---|
| 셀(Cell) | 2170 원통형 배터리 1개 (재) |
| K | 1,000개. 모든 주문·생산·재고 수량의 단위 (예: 15,000K = 약 1,500만 개) |
| 한국 | 배의 출발·도착지(본사·항만). 공장이 아니다 (재) |
| 완제품 재고 창고 | 공장마다 있고, 선적 전까지 생산된 셀을 보관한다 (재) |
| 재고 상한 | 공장 창고가 보관할 수 있는 최대 수량(K). 도현 문서의 "창고 한도"와 같은 말이다 |
| 마스터 데이터 | 계산의 기준 값. 공장별 하루 생산량·재고 상한·셀당 원가, 나라 간 항해 일수, 배 척수·하루 운항비 |
| 마스터 버전 | 마스터를 저장할 때마다 오르는 번호. 시뮬레이션 이후 바뀌었는지 판단한다 |
| 경로(안) | 선박을 어떻게 운영할지에 대한 계산 결과 하나 |
| 소요 일수 | 마지막 배가 한국에 돌아오는 날 |
| 배분 (권/재) | 총 주문 수량을 4개국 공장에 나눠 맡기는 것 |

## 5. 핵심 업무 흐름

수량 입력 → 경로 비교 → 하나 골라 확정 → 상태 관리(확정 → 진행 → 완료)
마스터 데이터(공장 생산 능력, 항해 일수, 운항비)를 관리하면 그 뒤의 계산부터 반영된다.

## 6. 기능 요구사항

### FR-1. 마스터 데이터 관리
- 공장별 하루 최대 생산량(K), 재고 상한(K), 셀당 생산원가(원)를 관리한다.
- 한국을 포함한 5개 나라의 모든 쌍(10개)에 대한 항해 일수를 관리한다. 1~365일의 정수. (재/권)
- 배 척수(1~4)와 척당 일 운항비(억 원 단위 입력, 원 단위 정수로 떨어져야 함)를 관리한다. (재/권. 도·준은 "배 척수"만 적음) **[차이 B2]**
- 잘못된 값이 하나라도 있으면 아무것도 저장하지 않고 이유를 한꺼번에 알려 준다.
- 저장할 때마다 마스터 버전이 오른다.
- 바꾼 값은 그 뒤의 계산부터 적용된다. 이미 확정한 주문은 그대로다.
- 마스터가 비어 있으면 기본값으로 채운다. (재/권)

### FR-2. 주문 입력과 경로 시뮬레이션
- 입력은 총 생산 필요 수량(K)과 이를 4개 공장에 나눈 공장별 수량이다. 음수는 불가이고 총합은 1K 이상 100,000K 이하이며, 공장별 합은 항상 총량과 같다. (재/권/준)
- **원문과 코드의 차이 [차이 B14]**: 원문의 일일 최대 생산량 예시는 "0.1K 개/일"인데, 시스템은 K를 정수로만 받는다(최소 1K). (재. 코드로 확인함)
- 생산 물량 배분: **[미정 A4]** 시스템이 계산·추천해야 하는지, 담당자가 정하도록 돕는 것인지. 현재는 사람이 게이지로 조정한다.
- 나라별 수량이 정해지면 서버가 경로를 계산해 한 번에 비교해 보여 준다. **[미정 A3]** 아래 3안을 요구사항으로 확정할지 구현 선택으로 둘지
  - 운항비 최소(COST): 운항비가 가장 낮은 안. 같으면 더 빠른 쪽
  - 가장 빠르게(FAST): 소요 일수가 가장 짧은 안. 같으면 더 싼 쪽
  - 가까운 곳부터(NEAR): 한국에서 가까운 나라부터 차례로 배에 나눠 배정하는 단순한 안
- 경로마다 소요 일수, 생산비, 운항비, 총 비용, 배별 왕복 일정(출항일·방문 나라·도착일·싣는 양·귀환일)을 보여 준다. 나라별 일별 재고·생산량과 필요 방문 횟수도 보여 준다. (재/도/권)
- 시뮬레이션만으로는 아무것도 저장하지 않는다. (도/재/권)

### FR-3. 주문 확정
- 마음에 드는 경로를 고르고 메모(선택, 1,000자 이하)를 남겨 확정한다. (재/권)
- 확정 직전에 서버가 같은 입력으로 다시 계산한다. 화면이 보낸 숫자를 믿지 않는다.
- 시뮬레이션 후 마스터가 바뀌었으면 확정을 거부하고 다시 시뮬레이션하게 안내한다. (일반 오류와 구분되는 충돌)
- 확정한 주문에는 그 시점의 마스터 값, 주문 수량, 방문 횟수, 선택한 경로 전체를 함께 저장한다. 마스터가 나중에 바뀌어도 옛 주문의 내용과 비용은 변하지 않는다.
- 확정 시 첫 상태 이력(없음 → 확정)을 남긴다. (재/권)

### FR-4. 주문 조회
- 주문은 목록에 등록되어 한눈에 현황을 볼 수 있다. 최신순이고, 상태별로 걸러 볼 수 있으며, 상태별 건수를 보여 준다.
- 주문 상세에서 확정 정보(시각, 확정자, 수량, 경로, 일수, 비용, 메모), 계획 내용, 상태 변경 이력을 볼 수 있다.
- 주문 기록에는 만든 사람, 상태를 바꾼 사람이 남는다. (재)
- 취소된 주문을 목록에 남길지 **[미정 A1]**

### FR-5. 주문 상태 관리
- 상태는 확정 → 진행 → 완료 순서로 진행한다. 확정·진행 상태에서는 취소할 수 있다.
- 완료와 취소는 마지막 상태라 더 바꿀 수 없다.
- 상태를 바꿀 때마다 이전 상태, 새 상태, 변경자, 시각을 이력에 남긴다.
- 두 사람이 같은 주문을 동시에 바꾸면 한쪽의 변경만 반영하고, 다른 쪽에는 새로고침 후 다시 시도하라고 안내한다. (낙관적 락)
- 상태 변경은 모두 담당자가 수동으로 한다. 완료를 날짜·계획과 연동해 자동으로 바꾸지 않는다. (권/재) **[차이 B4]**
- 취소된 주문의 처리 **[미정 A1]**: 취소 상태로 목록에 남긴다(권/재), 주문은 삭제하고 이력만 남긴다(준), 삭제 여부는 언급 없음(도)

| 상태 | 의미 (요구사항 원문) |
|---|---|
| 확정 | 고객사와 소통되어 주문을 구두로 확정한 상태 |
| 진행 | 계약서를 작성 후 공장 생산 및 운영을 시작한 상태 |
| 완료 | 생산이 완료되어 한국으로 물량이 모두 들어온 상태 |
| 취소 | 어떤 사정으로 인해 취소된 상태 (확정 / 진행 중에 취소 가능) |

### FR-6. 이해하기 쉬운 표시
- 큰 금액은 억 원 단위로 보여 준다. 내부 저장은 원 단위 정수다. (도/준/재/권)
- 계획을 지도 위 배의 이동으로 보여 준다. (도만 요구사항으로 적음. 권은 원문에 없는 구현으로 표시) **[차이 B13]**
- 입력 오류와 규칙 위반은 이유를 사람이 읽을 수 있는 문장으로 알리고, 내부 오류와 구분한다. (재/준/도)

### FR-7. 인증
- 로그인하지 않으면 로그인 화면으로 보낸다. (도/준/재. 권은 원문에 없다고 표시) **[미정 A5]**
- 로그인하지 않은 `/api/**` 요청은 401로 거절한다. (재. 코드로 확인함)

### FR-8. 추가 개발 필요 (권/재) **[미정 A2]**
- 주문 시 고객사를 입력받는다.
- 주문 시 필요 납기를 입력받는다. 납기를 경로 계산에 반영할지는 원문에 없다.
- 국가별 공장 운영비를 관리한다 (국가별로 상이). 총비용에 어떻게 더할지, 도입하면 COST 기준을 운항비만 볼지 총비용을 볼지 정해야 한다. (재)

## 7. 업무 규칙 (계산의 기준)

1. 생산은 주문 즉시 모든 공장에서 동시에 시작한다(0일차). (4명)
2. 하루 생산량 = min(하루 최대, 재고 상한 − 현재 재고, 남은 주문). 공장은 재고 상한을 넘게 쌓지 못하고, 창고가 차면 배가 가져갈 때까지 생산이 멈춘다. 재고는 어느 날에도 재고 상한을 넘지 않는다. (재/도/권)
3. 배는 도착한 순간 쌓여 있는 재고를 전부 싣는다. 선박 적재량은 제약이 아니다.
4. 주문이 재고 상한보다 많으면 여러 번 방문한다. 방문 횟수 = 올림(주문 ÷ 재고 상한). 마지막 방문 전까지는 재고 상한만큼, 마지막은 나머지를 싣는다. 주문이 없는 나라는 가지 않는다.
5. 한 나라는 한 척의 배만 방문한다. (도/준/재) **[미정 A8]** 요구사항 원문에는 없다. 여러 척이 나눠 방문해도 되는지는 설명에 없다.
6. 여러 번 방문할 때는 한국에 돌아와 짐을 내리고 다시 출항한다. 배는 한국에서 출발해 한국으로 돌아온다.
7. 배는 재고가 채워지는 날에 맞춰 가능한 한 늦게 출항한다. 한국에서 기다리는 시간은 비용이 없다.
8. 사용하는 배는 설정된 척수를 넘지 않는다. (재/권) 주문이 있는 나라 수보다 많은 배는 쓰지 않는다. (권)
9. 생산비 = 주문 수량(K) × 1,000 × 셀당 원가. (재/권. 도현 문서는 단위 표기가 빠져 있음, 차이표 D2)
10. 운항비 = 배가 바다에서 보낸 날수 × 하루 운항비 (항구 대기일 제외)
11. 총 비용 = 생산비 + 운항비. 공장 운영비는 포함하지 않는다 **[미정 A2]**
12. 모든 경로는 주문한 수량을 정확히 수거한다. 계획이 끝나면 수거량과 주문량이 맞는지 검산하고, 어긋나면 오류로 처리한다. (재/도/권)
13. 운항비 최소 안은 세 경로 중 운항비가 가장 낮고, 가장 빠르게 안은 소요 일수가 가장 짧아야 한다. (재/도)
14. 한국 항만·창고에는 재고 한도가 없다. (권) **[차이 B1]**
15. 주문은 서로 독립적으로 계산한다. 이미 확정된 다른 주문의 생산·재고는 고려하지 않는다. (권) **[차이 B3]**

예시: 중국 5,000K 주문, 재고 상한 4,000K → 방문 올림(5,000 ÷ 4,000) = 2회. 첫 방문에 4,000K, 마지막 방문에 1,000K를 싣는다. (권)

## 8. 데이터 요구사항

- 생산 수량은 K, 금액은 원 단위 정수로 저장하고, 억 원 변환은 표시할 때만 한다. (도/준/재)
- 확정한 주문은 그 시점의 마스터 값과 계획을 함께 저장하고, 이후 마스터가 바뀌어도 변하지 않는다.
- 취소 주문의 처리 **[미정 A1]**
- 주문과 마스터는 파일 DB에 저장돼 서버를 다시 시작해도 남는다. (권/재) **[차이 B5]**

## 9. 비기능 요구사항

| 항목 | 내용 |
|---|---|
| 정합성 | 확정은 서버 재계산 결과만 믿는다. 클라이언트가 보낸 값은 신뢰하지 않는다 |
| 동시성 | 같은 주문을 동시에 바꾸면 한쪽을 거부한다 (낙관적 락) |
| 오류 안내 | 사용자 입력 오류는 이유를 쉬운 한국어로 알리고 내부 오류와 구분한다 |
| 정확성 | 같은 입력이면 같은 계획이 나오고, 수거량과 주문량이 맞지 않는 계획은 내보내지 않는다 (도/재) |
| 응답 속도 | 가장 큰 주문도 사용자가 기다릴 수 있는 시간 안에 계산된다 (도) |
| 실행 환경 | Java 17 + Spring Boot, 서버 렌더링(Thymeleaf), 파일 기반 H2 DB (재) |

## 10. 화면

로그인, 주문 목록, 주문 추가(수량 입력·시뮬레이션·확정), 주문 상세(계획과 상태 이력), 마스터 데이터

## 11. 인수 기준 (준)

1. 로그인하지 않고 화면 주소로 접근하면 로그인 화면이 나온다.
2. 새 주문 화면에서 공장별 수량을 입력하고 계산하면 경로 3종의 소요 일수와 비용이 나온다.
3. 경로를 골라 확정하면 주문 목록에 "확정" 상태로 나타나고, 상세에서 확정 당시의 계획을 볼 수 있다.
4. 주문 상세에는 현재 상태에서 허용된 변경 버튼만 보인다. 완료·취소된 주문은 더 바꿀 수 없다.
5. 계산한 뒤 마스터를 저장하고 확정하면 오류 안내가 나오고, 이미 확정한 주문의 내용은 그대로다.
6. 수량이 없거나 상한(100,000K)을 넘는 주문은 이유가 화면에 안내되고 계산되지 않는다.
