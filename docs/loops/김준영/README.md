# 개발 Loop 설계 (prepare → implement → verify)

요청 하나를 받아 **계획 → 구현 → 검증**까지 에이전트로 끝내는 개발 루프의 설계 설명이다. 이 문서는 설계만 다루고, 구현 파일(워크플로·스크립트·에이전트 정의)은 포함하지 않는다.

## 1. 핵심 원칙

1. **단계 사이는 파일로 된 계약과 구조화된 결과로 연결한다.** 상태는 대화가 아니라 파일에 둔다. 그래서 중간에 멈췄다가 같은 입력으로 다시 실행하면 파일 상태에서 이어갈 수 있다.
2. **통과·중단 판정은 에이전트가 아니라 스크립트(종료 코드)가 한다.** 에이전트는 만들고 의견을 낼 뿐, "됐다"고 선언하지 못한다.
3. **테스트를 쓰는 에이전트와 구현하는 에이전트를 분리한다.** 같은 에이전트가 둘 다 쓰면 테스트가 구현에 맞춰진다.
4. **사람이 반드시 확인하는 지점을 둔다.** 계약(spec)이 틀리면 이후 단계가 전부 낭비되기 때문이다.
5. **실패하면 자동으로 우회하지 않고 근거를 남기고 멈춘다.**

## 2. 전체 흐름

```
prepare ─ 환경 점검(스크립트) → planner(plan·spec·영향도) → spec 게이트
          └─ [사람 승인 1] plan·spec·영향도 확인 → 브랜치 생성
slice   ─ slicer → steps 게이트
          └─ [사람 승인 2] step 분해 확인
implement (step 1..N 순서대로, step마다 최대 3회)
          test-writer → red 게이트 → implementer → 테스트 게이트 → step 커밋
verify  ─ verifier(체크리스트 판정 + 전체 테스트) → 성공 / 실패
```

한 번에 코드를 고치는 에이전트는 하나뿐이다(step 순서대로 직렬). 읽기만 하는 단계끼리만 병렬이 가능하다.

## 3. prepare — 무엇을 할지 확정한다

### 3-1. 환경 점검 (스크립트)
구현 전에 개발 가능한 상태인지 확인한다. 순서는 다음과 같다.
1. 작업 트리가 clean한가. 아니면 중단.
2. 원격 `main`을 fast-forward로만 최신화한다. 갈라져 있으면 merge·rebase 없이 중단.
3. 기존 단위·통합 테스트(baseline)를 실행한다. 실패가 있어도 중단하지 않고 목록만 기록한다. verify에서 "기존 실패"와 "새 실패"를 구분하는 기준이 된다.

브랜치는 항상 최신 `origin/main`에서 새로 만든다. E2E는 실제 DB를 오염시키므로 환경 점검에 넣지 않는다.

### 3-2. 계획과 영향도 분석 (planner)
planner는 코드와 테스트를 쓰지 않고 문서만 쓴다.

| 산출물 | 읽는 쪽 | 내용 |
| --- | --- | --- |
| `plan.md` | 사람 | 요청 해석, 발견한 사실과 근거, 위험 |
| `spec.md` | 사람 + 에이전트 | 계약. 목표, 가정, 수락 기준(AC), 수정 허용 범위, 시그니처, 제약, 범위 밖, 열린 질문 |
| `logs/impact.json` | 스크립트 + verifier | 영향도 분석을 구조화한 것 |

- **spec은 "무엇을"만 적는다.** test-writer가 spec만 보고 테스트를 쓰므로 구현 방식이 들어가면 테스트가 그쪽으로 기운다(시그니처만 예외).
- **AC는 관찰 가능한 입력과 결과 한 문장**으로 쓴다. "잘 동작한다" 같은 AC는 테스트로 옮길 수 없다.
- **영향도 분석은 환경 점검이 아니라 planner가 한다.** 코드를 읽어야 알 수 있기 때문이다. 담는 것은 이미 구현된 것(근거와 충분성), 영향받는 파일·테스트, 충돌할 수 있는 핵심 규칙, 위험과 대응이다.
- 요청한 기능이 **이미 구현돼 있으면** spec을 억지로 만들지 않고, 무엇이 부족한지 열린 질문으로 올린다.

### 3-3. spec 게이트와 승인
스크립트가 섹션 존재, AC 1개 이상, 수정 허용 범위의 파일 존재, 열린 질문 없음을 검사한다. 영향도도 검사한다: 신호등이 RED가 아니고, 이미 구현된 것 중 충분한지 "불명"이 없고, 영향받는 파일이 수정 허용 범위 안에 있어야 한다.
통과하면 **사람이 승인**한다. 승인 전에는 브랜치를 만들지 않고 implement로 가지 않는다. 승인 시점의 spec 해시를 기록해 이후 spec이 바뀌면 감지한다.

### 3-4. prepare 리포트 (두 단계로 쌓는다)
사람용 HTML은 에이전트가 직접 쓰지 않고, 스크립트가 JSON에서만 렌더링한다. JSON과 HTML이 어긋나지 않고 몇 번을 실행해도 결과가 같다.
- 1단계: 환경 점검 결과(`precheck.json`)
- 2단계: planner의 영향도 분석(`impact.json`)을 합쳐 한 화면으로 보여 준다. 영향도가 아직 없으면 "대기 중"으로 표시한다.

## 4. slice — TDD 가능한 작은 단위로 나눈다
승인된 spec을 slicer가 step 3~5개로 나눈다. 나누는 기준은 **AC 단위의 수직 조각**(계층별 분할이 아님)이며, step이 끝날 때마다 빌드와 기존 테스트가 green이어야 한다. 모든 AC는 한 step이 맡는다. test-writer는 구현을 보지 못하고 spec은 "무엇을"만 적으므로, 쪼개기는 이 단계에서만 한다.
- 스크립트 게이트: spec 미변경, 모든 AC 배정, step의 수정 범위가 spec 범위 안, 의존 순서 정상.
- 진행 상태(`pending → in_progress → completed`, 시도 횟수, 커밋)는 **스크립트만** 기록한다. 한 칸에 쓰는 주체는 하나다.
- 두 번째 **사람 승인**으로 step 분해를 확인한다.

## 5. implement — step마다 테스트 먼저
step 하나의 순서는 다음과 같다.
1. **test-writer**: spec과 이 step의 문서만 보고 테스트를 쓴다. 구현 코드(`src/main`)는 읽지 않는다. 필요한 시그니처는 빈 스텁만 만든다. 테스트는 정상·경계값·잘못된 입력을 다루고 given/when/then 구조로 쓴다. 계층별로 순수 계산은 Spring 없이, 서비스는 Test Double, 컨트롤러는 슬라이스 테스트로 가볍게 나눈다.
2. **red 게이트(스크립트)**: 테스트 결과 XML을 파싱한다. step의 AC마다 최소 한 개의 테스트가 **AssertionError로 실패**해야 한다. 컴파일 오류나 스텁이 던진 예외로 실패한 것은 인정하지 않고 test-writer로 되돌린다. 처음부터 항상 통과하는 테스트를 걸러내기 위해서다.
3. **implementer**: 테스트를 통과시키는 **최소한의 구현**만 쓴다. 테스트 파일은 수정하지 못하고, 테스트가 AC와 어긋난다고 판단하면 고치지 않고 "테스트 이의"로 올린다. 요구에 없는 기능·추상화·주변 리팩터링은 하지 않는다.
4. **step 게이트(스크립트)**: 전체 테스트(E2E 제외) 통과, step의 수정 범위 안의 변경만 있는지 확인하고, 통과하면 step 단위로 커밋한다.

실패는 원인별로 라우팅한다: 코드 결함 → implementer, 테스트 결함·이의 → test-writer, spec 모호 → 사람. step당 최대 3회이며, 못 넘기면 근거를 남기고 중단한다.

## 6. verify — 약속을 지켰는지 확인한다
**verifier**는 코드를 고치지 않고 확인과 기록만 한다.

1. **체크리스트 판정**: plan·spec·영향도에서 항목을 빠짐없이 뽑는다(AC, 수정 범위, 시그니처, 제약, 범위 밖, 위험, step 완료, 영향도, 핵심 규칙). 항목마다 **PASS / FAIL과 근거**(파일:줄, 테스트 이름, 실행 결과)를 적는다. 근거 없는 PASS는 없다. 테스트가 통과했더라도 AC를 실제로 단언하지 않으면 FAIL이다.
2. **전체 테스트**: 하나도 빼지 않고 실행해 결과 XML로 집계한다. 실패·오류·skipped는 모두 FAIL이고, 실패한 테스트는 이름과 원인, 위치, 기존/신규 여부, 원인 분류를 기록한다. E2E는 실제 DB 보호를 위해 실행하지 않고 한계로 명시한다.
3. **영향도 예측 대조**: planner가 예측한 영향 파일과 실제 변경 파일을 비교한다. 예측에 없던 변경이 있으면 영향도 분석이 놓친 것이므로 YELLOW 사유로 남긴다.

### 신호등
항목은 PASS/FAIL 둘뿐이고, 종합과 영역별 판단은 규칙으로 정한 신호등으로 낸다.

| 색 | 의미 |
| --- | --- |
| RED | FAIL 항목, 테스트 실패·skipped, 빌드 실패, 테스트 미실행 중 하나라도 있음 |
| YELLOW | 통과했지만 확신하지 못하는 것이 남음(미확인 가정, E2E에 미칠 영향, 예측에 없던 변경 등) |
| GREEN | 남은 것 없음 |

영역(요구사항, 범위·규칙, 계획 위험, 테스트·빌드)별로 색을 내고 종합은 가장 나쁜 색이다. RED만 실패로 보고, YELLOW는 통과지만 사람이 사유를 확인한다.

### 산출물 (두 가지)
- AI용 `verify.json`: 항목별 판정, 테스트 집계, 실패 건의 담당(route)과 step, 무진전 감지용 키.
- 사람용 `report.html`: **① 판단 결과(신호등) → ② 테스트 결과 → ③ 결론** 순서. JSON에서만 만든다.

## 7. verify가 실패하면 — 사람이 정한다
verify가 끝나면 최종 결과는 **성공 / 실패**뿐이다. 실패했을 때 prepare로 **자동으로 되돌리지 않는다.**

- prepare에는 사람 승인이 필수라서, 자동으로 되돌리면 승인을 우회하거나 사람 없이 멈춘다.
- 실패의 대부분은 코드·테스트 결함이라 prepare까지 갈 일이 아니다.
- 승인된 spec이 바뀌면 이후 게이트가 모두 깨지므로, 재승인 절차가 필요하다.
- 같은 실패를 반복하는 무한 루프를 막아야 한다.

그래서 실패 종류별로 나눈다.

| 실패 종류 | 처리 |
| --- | --- |
| 코드 결함, 테스트 결함 | verify 안에서 해당 step으로 라우팅해 자동 보완. 최대 3회 |
| spec 모호, 범위 밖 변경 | 즉시 실패. 사람에게 넘김 |
| 같은 실패가 두 회차 연속 | 무진전으로 실패 |

무진전은 실패 키(라인 번호를 뺀 항목 ID·테스트 이름)가 이전 회차와 같으면 코드가 개선되지 않은 것으로 본다. 일부라도 줄었으면 진전이다.
실패로 끝나면 `handoff.md`에 증거(중단 사유, 반복된 실패의 원문, 회차별 변화, 시도한 수정, 관련 파일)를 남기고, 사람이 보고서를 보고 **prepare로 보완할지, 직접 고칠지** 결정한다.

## 8. 파일 배치
모두 `.plans/<slug>/` 아래(git 제외, 로컬 전용)에 둔다. 사람용과 AI용 폴더를 나누지 않고, 같은 내용을 두 형식으로 두지 않는다.

| 파일 | 읽는 쪽 | 쓰는 주체 |
| --- | --- | --- |
| `plan.md`, `spec.md` | 사람 + 에이전트 | planner |
| `prepare-report.html` | 사람 | 스크립트(JSON에서 렌더링) |
| `steps/index.json`, `steps/NN-*.md` | 에이전트 + 스크립트 | 정의는 slicer, 진행 상태는 스크립트만 |
| `report.html` | 사람 | verifier(JSON에서 만듦) |
| `handoff.md` | 사람 | 실패 시 기록 |
| `logs/` | 에이전트 + 스크립트 | 환경 점검, 영향도, 승인 기록, step별 red 결과, verify 결과 등 기계 출력 |

## 9. 이 프로젝트에 맞춘 주의점
- **E2E(Playwright)는 루프에 넣지 않는다.** 실제 DB를 사용해 데이터가 쌓이기 때문이다. 루프의 게이트는 단위·통합 테스트까지만 쓰고, E2E는 별도 DB를 쓰거나 사람이 수동으로 돌린다.
- 영향도와 검증에서 항상 확인하는 **프로젝트 불변식**: 주문 확정 시 서버 재계산, 시뮬레이션 이후 마스터 버전이 바뀌면 확정 거부, 낙관적 락, 로그인 인터셉터 우회 여부.
- 코드 스타일(탭 들여쓰기, 한국어 주석·메시지, 계산 로직은 DB·웹에 의존하지 않기)을 구현과 검증의 기준에 포함한다.

## 10. 한계와 앞으로의 과제
- 사람 승인은 spec과 step 분해 두 곳으로 정했다. 최종 머지 전 확인은 아직 정하지 않았다.
- step 게이트는 전체 테스트가 모두 통과해야 하므로, baseline에 실패가 있는 상태에서는 모든 step이 막힌다. baseline 실패와 새 실패를 구분하는 판정은 아직 반영하지 않았다.
- 실패 후 prepare로 돌아가는 재승인 절차(같은 브랜치에서 spec을 다시 승인하는 흐름)는 지원하지 않는다. 필요해지면 그때 설계한다.
- 성능, 코드 스타일 같은 추가 리뷰어는 두지 않았다.
- 규모: 한 회차에 에이전트가 test-writer와 implementer 위주로 돌고, 3회전까지 늘어날 수 있다. 비용이 문제가 되면 verify의 병렬 리뷰어를 줄이는 방향으로 조정한다.
