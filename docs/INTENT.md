# INTENT — 배터리 주문·생산·선박 운영 계획 프로그램 (취합본)

> 취합 대상: 권웅기(권), 김도현(도), 김재연(재), 김준영(준) — 4명 전원
> PRD가 "무엇을"이라면 이 문서는 "왜"를 적는다. 4명이 같은 의도를 적은 것은 그대로 올렸고, 일부만 적었거나 갈리는 것은 항목 끝에 **(권/도/재/준)** 으로 출처를 적었다. **[미정 Ax]**, `Bx`, `Dx`는 `docs/취합-차이표.md`의 ID다.
> 근거 표시: **[요구사항]** 원문에 직접 적힘 / **[코드]** 코드·테스트·주석에서 확인 / **[추정]** 근거가 약한 해석. 팀이 직접 밝힌 것이 아닌 설계 의도는 코드에서 읽어 낸 것이라 틀릴 수 있다. (재)

## 1. 목적

### 1.1 풀려는 문제
DSD는 4개국 공장을 직접 운영하면서 배를 빌려 물량을 한국으로 들여온다. 주문이 들어올 때마다 "어느 공장에서 얼마나 만들고, 배를 어떻게 돌려 실어 올지"를 정해야 하고, 이 결정이 생산원가와 선박 임차비(하루 약 1억 원)를 크게 좌우한다. 공장마다 하루 생산량, 창고 크기, 원가, 거리가 달라서 사람이 따지기 어렵다. 이 일을 경로 여러 안을 즉시 계산해 비교하고, 결정한 내용을 그대로 남기는 일로 바꾼다. (도/준/재)

### 1.2 역할의 경계
- 결정을 대신하지 않고 돕는다. 정답 하나를 강요하지 않고 **비용·속도·단순함** 세 관점의 후보를 나란히 보여 준다. 고르는 일과 확정은 담당자가 하고, 계산은 시스템이 맡는다. (도/재)
- 시스템의 책임은 **계산의 정확성**과 **기록의 신뢰성**이다. (도)
- 최적 운영 시스템이 되려는 것이 아니다. 주문 시점의 계획을 계산하고 확정 기록을 남기는 데서 멈춘다. (준)
- 선택한 계획을 그대로 기록해 두어, 나중에 "그때 왜 이렇게 정했는지" 다시 볼 수 있게 한다. (재)
- 주문 상태(확정 → 진행 → 완료/취소)는 실제 영업·생산 단계를 따른 기록이다: 구두 확정 → 계약서 작성 후 생산 시작 → 한국 입고 완료. (재) [요구사항]
- 이 경계 중 "생산 물량 배분도 사람이 정한다"는 부분은 요구사항 원문과 맞는지 **[미정 A4]**

### 1.3 성공의 모습 (도)
- 담당자가 수량만 넣고 비용과 시간의 맞바꿈을 바로 이해한다.
- 확정한 주문은 시간이 지나도 그때의 계획과 비용 그대로 확인된다.
- 계산 결과를 의심할 일이 생기지 않는다.

## 3. 계산 규칙의 업무적 이유 (재)

- **가능한 빨리 생산 시작**: 업무 설명의 "주문이 접수되면 가능한 빠르게 생산을 시작해 재고 창고에 보관". 그래서 0일차에 모든 공장이 동시에 시작한다. [요구사항]
- **재고 상한과 여러 번 방문**: 공장 창고가 작아 한 번에 다 못 쌓는다. 상한을 넘는 주문은 한 번 실어 가 비운 뒤 다시 채워 수거한다. 한국으로 돌아와 다시 나가는 이유도 이것이다.
- **적재량은 제약이 아님**: 컨테이너 적재량이 충분하므로 배 용량을 계산하지 않는다. 배 수가 곧 동시 운항 수다. [요구사항]
- **NEAR는 최적이 아니다**: 비교용 기준선이다. 최적화를 기대하는 변경은 COST/FAST 쪽에 한다.

## 4. 앞으로 바꿀 때 지킬 것

기능이 늘거나 규칙이 바뀌어도 유지한다. 깨야 한다면 PRD와 이 문서를 먼저 고친다. (도/재) **[차이 A7]**

반드시 지킬 것 (도/재)
1. 확정한 주문은 불변이다. 마스터·규칙·계산 방식이 바뀌어도 과거 주문의 내용과 비용은 변하지 않는다. (저장된 `planJson`은 그대로)
2. 돈과 일정은 시스템이 만든다. 서버가 다시 계산하고, 클라이언트가 보낸 계획·비용을 저장하지 않는다.
3. 낡은 계산으로 확정하지 않는다. 계산에 영향을 주는 마스터가 바뀌면 버전을 반드시 올리고, 바뀐 뒤에는 다시 계산하게 한다.
4. 틀린 결과를 조용히 내보내지 않는다. 검산은 약화하지 않는다. 모든 경로는 수거량 = 주문량이고, 재고는 상한을 넘지 않는다.
5. 모든 경로안은 같은 업무 규칙을 따른다. 새 경로를 추가해도 PRD 업무 규칙을 어기지 않고 같은 검산을 통과해야 한다.
6. 사람이 고른다. 시스템이 경로를 자동으로 확정하지 않는다.
7. 동시에 써도 서로 덮어쓰지 않는다.
8. 이력은 지우지 않는다. 누가, 언제, 무엇을 바꿨는지는 남는다. (※ "취소 시 주문 삭제" **[미정 A1]** 와 충돌 여부 확인 필요)
9. 상태 전이는 `OrderStatus` 한 곳에서만 정의한다. 화면 버튼, 서비스 검사, PRD가 모두 이를 따른다. (재)
10. 운항비 최소 ≤ 다른 경로의 운항비, 가장 빠르게 ≤ 다른 경로의 소요 일수. 테스트 `costOptionIsNotMoreExpensiveAndFastOptionIsNotSlower`가 지킨다. (재)
11. 금액은 원 단위 정수다. 억 원은 표시에서만 변환한다. (재)
12. 한국 대기는 무료이고 항해일에만 임차비가 붙는다. 이를 바꾸면 "늦게 출항" 규칙의 근거가 사라진다. (재)
13. 한 나라는 한 척만 방문한다. 규칙을 바꾸면 일정 계산과 검증이 함께 바뀌어야 한다. (재) **[미정 A8]**
14. 계산 규칙을 바꾸면 `PlannerTest`를 먼저(또는 함께) 고친다. 기대 수치(예: 중국 400K → 왕복 2일)는 규칙의 문서이기도 하다. (재/도)

품질 기준 (도)
- 정확성: 같은 입력이면 같은 계획이 나오고, 수거량과 주문량이 맞지 않는 계획은 내보내지 않는다.
- 알기 쉬운 안내: 입력 실수나 규칙 위반은 이유를 쉬운 말로 알리고 내부 오류와 구분한다.
- 응답 속도: 가장 큰 주문도 사용자가 기다릴 수 있는 시간 안에 계산된다.

지키는 것이 좋은 것
- 계산 규칙을 바꾸기 전에 기준 예시(입력과 기대 결과)를 테스트로 먼저 고정한다. 결과를 출력만 하는 테스트는 값이 조용히 달라져도 알아채기 어렵다. (도)
- 숫자 정책(초기값, 한도)은 PRD가 아니라 마스터 화면과 설정에서 다룬다. (도) **[미정 A6]**
- 새 요구사항은 PRD → INTENT → 코드 순서로 반영하고, 의도가 바뀌면 INTENT를 먼저 고친다. (도) **[차이 A7]**

## 5. 알려진 한계

- 로그인은 고정 계정 하나(`admin`/`admin`)라 사용자 구분이 없다. 시연·내부 도구 수준이다. (준/권/재)
- 취소한 주문은 이력만 남고 되돌릴 수 없다. (준) **[미정 A1]**
- 주문 간 공장 용량이 공유되지 않는다. (권)
- 선박 적재 용량, 한국 쪽 재고·창고 용량은 계산하지 않는다. (권)
- 공장 운영비, 고객사, 납기는 아직 구현되지 않았다. (권/재) **[미정 A2]**
- **조합 폭발**: 나라 수·배 수를 늘리면 분할 × 방문 패턴 × 순서 탐색량이 급격히 늘어난다. 공장을 늘릴 때는 탐색 방식(휴리스틱·가지치기) 변경을 같이 검토한다. 총량 상한(100,000K)은 값 크기 제한이지 탐색량 제한이 아니다. (재)
- **나라 목록 고정**: 공장 4곳은 `Country` enum, 마스터 폼 키, 화면, 초기값에 흩어져 있어 나라를 추가하면 모두 함께 바꿔야 한다. (재)
- 원문의 "0.1K 개/일" 같은 소수 K는 입력할 수 없다. (재) **[차이 B14]**

## 7. 코드 리뷰 때 볼 질문 (재)

- 이 변경이 4장의 불변식을 깨지 않는가?
- 서버가 값을 다시 계산하는가, 아니면 화면 값을 믿고 있는가?
- 마스터 값이 바뀌는 경로에서 버전을 올리는가?
- 상태를 바꾸는 경로가 이력을 남기고 버전 충돌을 처리하는가?
- 계산 규칙을 바꿨다면 테스트의 기대 값도 의도적으로 바꿨는가?
- 요구와 현재 구현의 차이(PRD 12장)를 메우는 변경이라면, 지킬 방향을 따랐는가?

## 8. 요구와 구현의 차이를 메울 때 지킬 방향 (재)

| 항목 | 방향 |
|---|---|
| 공장 배분 | 배분은 `Planner` **앞단**에 둔다. `Planner`의 입력(나라별 수량)은 그대로 유지한다. 배분 결과도 사람이 고칠 수 있게 한다 |
| 공장 운영비 | 마스터와 확정 스냅샷에 포함하고 버전을 올린다. 부과 방식(일 단위·가동 일수 등)은 확인 필요. 도입하면 "COST = 운항비 최소"의 기준을 다시 정한다 |
| 고객사·납기 | 주문 정보로 저장한다. 납기는 계획의 소요 일수와 비교되는 값이므로 일수 계산의 의미를 바꾸지 않는다 |
| 취소 주문 | 삭제를 없애고 상태로 남기는 쪽이 요구에 맞다. 목록 건수, 필터, 상세 화면, 이력 조회가 함께 바뀐다 |
| 생산원가 범위 | "수준"이므로 입력 제한이 아니라 기준값으로 본다. 기본값(인도네시아 450원)을 바꿀지는 확인 필요 |

위 방향은 김재연 님이 제안한 것이며 아직 팀 합의가 아니다.

## 9. 팀이 정해야 할 것

PRD 12장의 A1~A8, 그리고 의도 쪽에서 아래가 더 있다.

- 공장 운영비를 일 단위·가동 기간·공장 수 중 무엇으로 부과하는가 (권/재)
- 일일 최대 생산량 같은 값에 소수 K(예: 0.1K)를 허용할 것인가 (재)
- 관리자 외 사용자가 생길 가능성이 있는가 (재)
